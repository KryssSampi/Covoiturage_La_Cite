Protocole de sécurité propriétaire Zero-Trust à certificats auto-générés rotatifs. Présent dans les trois tiers, déclenché selon des séquences rigoureuses et ordonnées. 01 Fondations

Concepts Fondamentaux

🔐
Double Verrou — Hardware + Identité
Deux barrières indépendantes qui ne fonctionnent jamais l'une sans l'autre. L'authentification institutionnelle (JWT via OTP envoyé à @lacitec.on.ca) prouve qui est l'utilisateur. Le certificat cryptographique dans l'enclave matérielle du téléphone prouve avec quel appareil précis il communique. Un attaquant possédant l'un sans l'autre ne peut rien faire.
Propriété: Non-répudiation totale · Imputabilité légale garantie
📜
Certificat Propriétaire Auto-Généré
Pas un SSL classique. Le Core Server est l'Autorité de Certification (CA) du système. Il génère des paires de clés ECC (Elliptic Curve Cryptography) — sécurité RSA-4096 équivalente avec des clés 10× plus courtes, optimisées pour mobile. Chaque certificat signe les requêtes et authentifie l'origine. Le Core possède la clé publique du client. Le client possède sa clé privée dans l'enclave matérielle (Keystore Android / Keychain iOS). La clé privée ne quitte jamais l'appareil.
Standard: ECC-P256 · Stockage: Hardware Secure Element
💓
Heartbeat Mobile — Éclaireur
Avant chaque requête métier, le mobile vérifie l'état de sa clé publique auprès du Core via un ping signé léger. Si la clé a tourné (HasGotNewPublicKey = false), le mobile bloque la transaction, déclenche l'authentification, et attend la nouvelle clé publique avant de continuer. L'utilisateur ne voit qu'un spinner — la sécurité opère en coulisses.
Fréquence: avant chaque session active · Délai: < 200ms
🔄
Rotation Irrégulière (Cible Mouvante)
Les certificats ne changent pas selon un calendrier prévisible. La rotation est déclenchée de façon aléatoire et irrégulière par le Core (quotidien / hebdomadaire / mensuel — personne ne sait quand). Cela élimine toute fenêtre d'anticipation pour un attaquant. Lors d'une rotation, tous les clients sont simultanément passés à HasGotNewPublicKey = false. Ils récupèrent la nouvelle clé publique lors de leur prochain Heartbeat confirmé.
Forward Secrecy: les sessions passées restent protégées même si une clé est compromise
⚡
Threads Parallèles — Zéro Latence
Le Core ne met pas la logique métier en attente de la validation sécuritaire. Deux threads s'exécutent en parallèle dès réception de la requête. Thread A (Métier) prépare la réponse SQL. Thread B (Sécurité) vérifie signature + comportement + clé. Au point de synchronisation, si B valide → on envoie. Si B échoue → Kill Switch, Thread A annulé, ressources libérées. L'attaquant ne peut pas mesurer le délai pour déduire quelle couche a rejeté sa requête (anti-timing-attack).
C#: Task.WhenAll + CancellationToken · Anti-Timing-Attack natif
🏛
Core Invisible — VPN + DNS Privé
Le Core Server n'a pas d'adresse IP dans les clients. Seul un nom de domaine privé (ex: core.lacite.internal) est embarqué. Ce domaine ne se résout que depuis l'intérieur du tunnel VPN. Pour le reste d'Internet, ce serveur n'existe pas. Le mobile utilise un VPN Always-on transparent pour l'utilisateur, avec Split-Tunneling : seul le trafic vers le Core passe par le tunnel. Un scan de port global ne trouvera jamais l'adresse du Core.
Mobile: VPN App-layer Always-on · Web: Whitelist IP interne + mTLS Serveur→Core
🔥
Cache-Purge & State Recovery
En cas d'anomalie critique, l'App mobile vide intégralement son cache local — clés, tokens, données utilisateur, préférences. L'appareil redevient une coquille vide. Un voleur qui forcerait l'accès ne trouverait aucune donnée exploitable. Mais le Core conserve l'état valide de l'utilisateur. Dès que l'authentification institutionnelle est re-confirmée, des requêtes de background recovery restaurent automatiquement l'état complet. Pour l'utilisateur légitime : reconnexion = retour à l'état normal.
Principe: l'App est jetable · Les données résident sur le Core · La clé réside dans l'enclave
📊
Journal Comportemental (UserActivity)
Chaque session enrichit le profil comportemental de l'utilisateur : lieu, heure, appareil, état des clés, compteur de requêtes étranges. Ce journal est la mémoire long-terme du Security Service. Il permet de distinguer un bug réseau légitime (même IP, même heure habituelle) d'une tentative malveillante (IP inconnue, heure 3h du matin, clé invalide). La non-répudiation devient alors un fait mathématique prouvable devant l'institution.
Stockage: SQL optimisé (ACID) · Rétention: 7 ans (PIPEDA) · Anti-Timing: comportement + machine

03 Tiers Mobile

Séquences Security Service — App Mobile

Mobile → Core via VPN Séquence 3.1 · Premier Enrôlement (installation + 1er login)
1
Activation VPN Always-on
Dès le lancement de l'App, le tunnel VPN est activé silencieusement en arrière-plan (Split-Tunneling : seul le trafic Core passe par le tunnel). Le nom de domaine core.lacite.internal devient résolvable.
2
Authentification Institutionnelle (JWT via OTP)
L'utilisateur entre son email institutionnel @lacitec.on.ca et reçoit un code OTP par email. Aucun certificat n'est encore présent — c'est la seule barrière active à ce stade. Le Core génère un token d'enrôlement temporaire (TTL: 5 minutes) après vérification du code OTP.
3
Génération de la paire de clés ECC-P256 dans l'enclave matérielle
L'App utilise Android Keystore / iOS Secure Enclave pour générer une paire (Clé Privée / Clé Publique). La clé privée est générée dans l'enclave — elle ne peut pas être exportée, même par l'App elle-même. La clé publique est récupérable.
4
Envoi de la Clé Publique au Core (Enrôlement)
L'App envoie au Core : DeviceFingerprint + PublicKeyPem + EnrollmentToken. Le Core crée un enregistrement ClientCertificate avec HasGotNewPublicKey = true.
5
Réception de la Clé Publique du Core (Bidirectionnel)
Le Core renvoie sa propre clé publique signée (le Core a aussi une paire). L'App la stocke dans son coffre local pour vérifier les réponses signées du serveur. La communication devient entièrement bidirectionnellement signée.
6
Configuration du mot de passe local (optionnel mais recommandé)
L'utilisateur peut configurer un mot de passe local de l'App (stocké localement, réinitialisable uniquement via authentification institutionnelle complète). Dès que l'App passe en arrière-plan, elle se scelle. Le cache peut être configuré pour se purger si l'App reste fermée > X minutes.
Mobile → Core via VPN Séquence 3.2 · Requête Métier Standard (session active, clé synchronisée)
1
Heartbeat pré-requête (éclaireur)
Avant d'envoyer la requête métier, l'App envoie un ping signé léger au Core pour vérifier l'état de sa clé : GET /security/heartbeat signé avec la clé privée. Le Core répond : key_valid ou rotation_required. Si rotation required → basculer vers Séquence 3.3.
2
Construction de la requête signée
L'App signe l'empreinte SHA-512 de la requête (URL + body + timestamp) avec sa clé privée ECC via l'enclave matérielle. La requête est envoyée avec le header X-Cite-Signature + X-Cite-Timestamp + X-Cite-UserId. Le timestamp empêche les attaques par rejeu (TTL signature: 30 secondes).
3
Core — Threads parallèles (métier + sécurité simultanés)
Voir Séquence 5.1 (Core). Le Thread A prépare la réponse. Le Thread B valide la signature + comportement + timestamp. Point de synchronisation avant envoi.
4
Réception de la réponse signée par le Core
L'App vérifie la signature du Core sur la réponse avec la clé publique du Core stockée localement. Si la signature est invalide, la réponse est rejetée silencieusement et l'anomalie est loggée localement pour le prochain Heartbeat.
Mobile ↔ Core Séquence 3.3 · Rotation de Clé (Heartbeat détecte HasGotNewPublicKey = false)
1
Heartbeat retourne rotation_required
Le Core a déclenché une rotation irrégulière. Tous les clients sont en HasGotNewPublicKey = false. Le mobile reçoit ce signal — aucune requête métier ne sera traitée tant que la rotation n'est pas confirmée. L'utilisateur voit un spinner neutre.
2
Vérification silencieuse — l'ancienne clé est-elle encore valide ?
Le Core accepte l'ancienne clé uniquement pour le handshake de rotation. Si l'ancienne clé est valide (PreviousPublicKeyPem correspond) → rotation fluide (Étape 3). Si la clé n'est ni l'actuelle ni la précédente → Kill Switch immédiat (Séquence 3.5).
3
Génération de la nouvelle paire ECC dans l'enclave
L'App génère une nouvelle paire (Privée B / Publique B) dans le Keystore. La requête de rotation est signée avec l'ancienne Clé Privée A pour prouver la continuité légitime de l'appareil.
4
Envoi atomique de la nouvelle Clé Publique B au Core
Le Core effectue une transaction atomique : il vérifie la signature avec l'ancienne clé A, puis remplace immédiatement A par B dans ClientCertificate. L'ancienne clé A devient PreviousPublicKeyPem (conservée 24h pour éventuelle désynchronisation réseau uniquement).
5
ACK de rotation + réception de la nouvelle Clé Publique du Core
Le Core confirme la rotation et renvoie sa propre nouvelle clé publique (le Core tourne aussi). L'App met à jour son coffre local, détruit l'ancienne clé privée A, passe HasGotNewPublicKey = true. La rotation est terminée.
Mobile → Institution → Core Séquence 3.4 · Certificat expiré hors période précédente (Re-enrôlement forcé)
1
Clé invalide — ni actuelle, ni précédente
Le Core rejette la requête. Le certificat est trop vieux ou corrompu. Aucune information n'est fournie au client sur la raison (anti-devin). L'App reçoit simplement un 401 CERT_INVALID.
2
Purge de cache locale déclenchée
L'App purge son cache local — clés, tokens, données session. L'appareil ne sait plus rien. Si l'App était ouverte : écran de reconnexion immédiat. Si en background : notification silencieuse + verrouillage à la prochaine ouverture.
3
Authentification institutionnelle complète obligatoire
Pas de shortcut. L'utilisateur doit passer par le flux OTP complet avec son email @lacitec.on.ca. C'est l'institution qui ré-autorise. Si le compte est en RequiresServiceDesk = true, l'authentification OTP est refusée et un message institutionnel s'affiche.
4
Re-enrôlement complet → Séquence 3.1 (étapes 3 à 6)
Une fois l'institution validée, le processus d'enrôlement repart de zéro. Nouvelle paire de clés générée. Le Core reconstruit l'état depuis la base de données. Les requêtes background recovery restaurent l'état de l'utilisateur.
Mobile — Déclenchement Kill Switch Séquence 3.5 · Anomalie critique détectée (côté mobile ou réponse Core)
1
Signal Kill Switch reçu du Core (ou détection locale)
Le Core envoie FORCE_LOGOUT + PURGE_CACHE dans la réponse (ou via notification push silencieuse si l'App est en background). Localement : si la vérification de la signature de la réponse du Core échoue, l'App déclenche elle-même le Kill Switch.
2
Purge intégrale du cache en < 500ms
Suppression : clé privée locale (révocable dans Keystore), tokens JWT, données utilisateur, cache SQLite, préférences session. L'appareil redevient une coquille vide. Aucune donnée sensible ne subsiste.
3
Affichage du Cooldown (selon gravité)
Niveau 1 (suspicion faible) : Avertissement discret + possibilité de reconnexion immédiate via SSO
Niveau 2 (incident) : Cooldown X minutes · Compte à rebours visible · SSO possible après délai
Niveau 3 (critique) : Blocage total · Appel au service client obligatoire · Vérification physique d'identité institutionnelle
4
Après Cooldown — Re-enrôlement → Séquence 3.4
La nouvelle clé publique est transmise uniquement après confirmation de l'authentification institutionnelle. Les requêtes background recovery restaurent l'état sans que l'utilisateur ne perde ses données métier.
04 Tiers Web

Séquences Security Service — Client Web

Navigateur → Web Server → Core Séquence 4.1 · Authentification et émission OpenWebSessionKey
1
Login JWT via OTP institutionnel
L'utilisateur entre son email @lacitec.on.ca et reçoit un code OTP. Après vérification du code, le Web Server génère un JWT. Pas de VPN nécessaire côté web — le Web Server est sur le réseau interne, le Core n'est accessible qu'à lui.
2
Web Server génère l'OpenWebSessionKey
Le Web Server génère une clé aléatoire cryptographiquement sûre (CSPRNG, 256 bits). Il la signe avec son propre certificat serveur (ServerSignature) et la stocke en base (WebSessionKey). Elle est envoyée au navigateur dans un cookie HttpOnly + Secure + SameSite=Strict. Le JavaScript de la page ne peut jamais lire cette clé.
3
Web Server s'authentifie auprès du Core (Serveur-à-Serveur)
Le Web Server possède son propre certificat de confiance enregistré sur le Core (un ClientCertificate de type web_server). Chaque requête vers le Core est signée avec ce certificat + l'ID de l'utilisateur. Pour le Core, il n'existe qu'un seul interlocuteur Web légitime : ce Web Server précis.
Navigateur → Web Server (TS) → Core Séquence 4.2 · Requête Métier Standard (session active)
1
Navigateur envoie requête avec cookie OpenWebSessionKey
Le cookie est automatiquement joint par le navigateur. Le JavaScript n'y a jamais accès (HttpOnly). Protection CSRF intégrée : l'OpenWebSessionKey sert aussi de jeton anti-CSRF pour les requêtes mutables (POST/PUT/PATCH/DELETE).
2
Web Server — Validation TypeScript en amont
Avant tout appel au Core : (1) Vérification OpenWebSessionKey valide en base. (2) Validation de schéma Zod stricte du body — toute propriété inconnue est rejetée (typage runtime). (3) Vérification CSRF token. Toute donnée "incomprise" est supprimée ici, le Core ne la voit jamais.
3
Web Server re-signe et transmet au Core
Le Web Server construit une requête interne avec : X-Cite-WebServer-Signature (certificat serveur) + X-Cite-UserId + X-Cite-RequestHash (intégrité). Le Core vérifie l'IP source (Whitelist : seul le Web Server) ET la signature du certificat Web Server.
4
Retour réponse → Web Server filtre → Navigateur
Le Web Server vérifie la réponse du Core (signature). Filtre les champs sensibles selon le rôle utilisateur (TypeScript). Renvoie uniquement ce que le client web est autorisé à voir.
Web — Kill Switch Séquence 4.3 · Anomalie Web détectée (côté Web Server ou ordre du Core)
1
Détection anomalie (Web Server ou signal Core)
Triggers : OpenWebSessionKey invalide / expirée · Trop de requêtes malformées (FailedValidationCount > seuil) · IP inhabituelle · Schéma Zod rejeté 3x de suite · Ordre FORCE_LOGOUT du Core.
2
Invalidation immédiate de l'OpenWebSessionKey en base
Status → revoked. Le cookie devient inutilisable même s'il est encore présent dans le navigateur. Toutes les requêtes suivantes avec cet ancien cookie sont rejetées instantanément.
3
Réponse HTTP : Clear-Cookie + Redirection page institutionnelle
Le cookie est effacé via Set-Cookie: expires=past. Le navigateur est redirigé vers une page d'erreur institutionnelle (pas d'information sur la raison — anti-devin). Cooldown appliqué selon gravité.
4
Re-authentification SSO → Séquence 4.1
Après cooldown, l'utilisateur refait le SSO institutionnel complet. Nouvelle OpenWebSessionKey émise. Journal comportemental mis à jour.

06 Cycle de Vie Clé

Chronologie d'une Rotation Complète

T₀ — Déclenchement Rotation Core (irrégulier, imprévisible)
Le Core génère de nouvelles clés ECC. Toutes les ClientCertificate.HasGotNewPublicKey passent à false en une transaction atomique. Un CertificateRotationEvent est créé. Le cache Redis des clés publiques est invalidé. Les clients ne savent pas encore que la rotation a eu lieu.
T₀ + Δ — Prochain Heartbeat Mobile (Lazy Pull)
Au prochain Heartbeat du client mobile, le Core répond rotation_required. Le mobile bloque ses requêtes métier, génère une nouvelle paire de clés ECC dans l'enclave, signe la demande avec l'ancienne clé encore valide. Séquence 3.3 complète.
T₀ + Δ + ε — ACK Mobile → HasGotNewPublicKey = true
Le Core reçoit l'ACK de confirmation. La nouvelle clé publique B remplace A. L'ancienne clé A passe en PreviousPublicKeyPem — uniquement disponible pour une éventuelle désynchronisation réseau pendant 24h. Le mobile peut reprendre ses requêtes normalement.
T₀ + 24h — Purge de l'ancienne clé A
PreviousPublicKeyPem = null. L'ancienne clé A n'existe plus nulle part dans le système. Tout appareil qui tenterait de se connecter avec A après ce point déclenchera un Kill Switch Niveau Élevé (Séquence 3.4). Forward Secrecy garantie : même si A était compromise, elle est maintenant inexploitable.
Clients Hors-Ligne Prolongés (absents pendant Δ)
L'ancienne clé A dans leur Keystore est toujours là — mais le Core ne l'accepte plus (après 24h). À leur retour, leur Heartbeat recevra rotation_required. Ils devront passer par la Séquence 3.3 (si dans les 24h) ou la Séquence 3.4 (re-enrôlement complet si après 24h).
T_N — Prochaine Rotation (timing imprévisible)
La prochaine rotation sera déclenchée à un moment aléatoire décidé par le Core. Personne — ni les développeurs, ni les utilisateurs, ni un attaquant qui observerait le trafic — ne peut prédire quand. C'est la cible mouvante : la fenêtre de vulnérabilité tend vers zéro.

08 Synthèse

Protocole "Imprenable" de La Cité

C# + TypeScript typage strict + Zod runtime. Toute donnée "incomprise" est détruite avant d'atteindre la logique métier. Les injections SQL/XSS n'ont aucune surface d'attaque.

Threads A (métier) + B (sécurité) simultanés. Zéro latence ajoutée. CancellationToken coupe tout si sécurité échoue. Anti-Timing-Attack natif : impossible de déduire quelle couche a rejeté.
